One log.
Different indexes over it.

LogEt is Danish and Norwegian for “the log”, and “et” also means “one”. Everything is stored once, in one append-only log on a local disk or in an S3 bucket. An index is a pure fold over that log. The first one is KV, and every index gets transactions, branches, time travel and provable deletion from the log.

Pre-1.0 and unreleased — not for production. The log, transactions and shred are model-checked and simulation-tested. Steady memory is still ~5–10× Pebble’s, full scans 3–5× slower, open ~10× slower; only MinIO is tested among object stores, there is no replication, and the format may change before 1.0.

30-second demo

Real output on a fresh local directory. Signatures differ on every run.

$ loget put greeting "hello"
{"lsn":1}
$ loget put greeting "hello, world"
{"lsn":2}
$ loget get greeting --at 1          # time travel
hello
$ loget put user/u17/email alice@example.com --subject alice
{"lsn":3}
$ loget tx '[{"op":"put","key":"stock/apple","value":"9"},…]'
{"lsn":4,"ops":2}
$ loget branch create exp            # zero-copy branch
{"heads":{"exp":4,"main":4},"ok":true}
$ loget put stock/apple 1000         # a bad write…
{"lsn":5}
$ loget rewind main 4                # …undone
{"heads":{"exp":4,"main":4},"ok":true}
$ loget shred alice                  # forget, provably
{"certificate":{…,"dek_deleted":true,"indexes_purged":["kv"],…},"valid_signature":true}
$ loget get user/u17/email
error (404): loget: not found
$ loget verify                       # CRCs, hash chains, fencing, shred proofs
{…,"ok":true,…}

One log, different indexes

The log is the only state. Each index folds it into whatever answers its queries fast, and can be rebuilt from it at any time.

one append-only log → indexes: KV · your index · next: topics · documents · vectors · full-text

Transactions for every index

Serializable optimistic concurrency with a single writer and group commit. An index tells the core what its answers read, and conflicts retry.

Branch, rewind, time travel

A branch is “parent log + LSN”, so nothing is copied. Read any key as of any LSN, undo a bad run, try a plan on a branch and promote it.

Provable deletion

Shredding a subject deletes its key: its values are unreadable on every index, branch and point in history. You get a signed certificate and the hash chain still verifies.

Write your own index

Declare the key spaces you own, fold records with Apply, drop a subject with DropSubject, optionally snapshot. How to write an index →

Simple to run

One static Go binary, no CGO. One URL: ./data or s3://bucket/prefix. No brokers, no Raft, no ZooKeeper.

Fencing without clocks

Create-only writes plus epochs. A zombie writer can never commit after a newer one opens.

KV first. Indexes reach main one at a time, each finished and benchmarked before the next. Topics, documents, vectors and cross-index transactions wait on branches. The pipeline →

Install

No release yet. Build from source with Go 1.27+: one binary for the CLI, the HTTP server and the engine.

git clone https://github.com/raman20/loget
cd loget && go build -o loget ./cmd/loget
./loget version

Or: go install github.com/raman20/loget/cmd/loget@main

On S3 or MinIO, change the URL:

export LOGET_URL='s3://my-bucket/app1?endpoint=127.0.0.1:9000&insecure=1&create=1'
loget put hello world

As a JSON/HTTP server:

loget serve --listen 127.0.0.1:7070 &
curl -X PUT localhost:7070/v1/kv/k -d v
curl localhost:7070/v1/kv/k

Embedded in Go (github.com/raman20/loget):

db, _ := loget.Open(ctx, "./data")
db.Update(ctx, func(tx *loget.Tx) error {
  v, _ := tx.Get("stock/apple")
  return tx.Put("stock/apple", next(v))  // retried on conflict
})

Where it does well

Point reads while the key index pages are resident; lower peak memory than Pebble during a 10M-key load and YCSB run; durable single-client writes on the journal layout; branches, time travel and shred that the others do not have.

Where it loses

Steady memory (mapped index pages and the Go heap stay resident), open time (the checkpoint load is O(index)), full scans, bulk writes, and compaction work that is O(keys): value chunks are shared between bases, but the key run is rewritten whole.

Honest status

Pre-1.0 and unreleased. Please don't put real personal data in it yet.

  • KV gaps, by impact: steady memory ~5–10× Pebble; open ~10× slower; full scans 3–5× slower; compaction rewrites the whole key run each time and pauses commits briefly; no value compression.
  • One writer per database, no HA, no replicas.
  • Only MinIO is tested (with fault injection); nothing on AWS S3, R2 or a real-world deployment yet. Run loget s3check first.
  • Keys and values without a subject are plaintext and are not covered by shred. In dev-key mode the key lives next to the data. Backups taken before a shred can still decrypt it.
  • The server has scoped bearer tokens and TLS and binds to 127.0.0.1 by default; no mTLS.
  • The on-storage format may change before 1.0.
